# @sazabi/deepsec-run-core

The trust core of deepsec.run: everything that answers "what happens to my code and my traces". It is deliberately small, readable, and standalone so it can be published read-only. The Next.js app (`apps/deepsec-run`) composes it with sessions, Postgres, admission, and the cron.

## Boundary

- No `@sazabi/*` dependencies and no database, HTTP framework, or UI. The only runtime dependency is `@vercel/sandbox`. Anything the app must supply (a template-failure reaction, adoption-failure reporting) comes in as a callback; the package never imports back.
- Public API is `src/index.ts` only. Moving code into this package must not change a byte of the scripts: `bun run check:deepsec-run-scripts` pins the SHA-256 of every script written into a sandbox (`_checks/deepsec-run-scripts/lib/pinned-digests.ts`). Editing a script means updating its pin in the same PR.
- What lives here: the pipeline scripts and fallback matcher (`src/scripts.ts`); the egress policy (`src/egress.ts`); the member/external scan limits (`src/limits.ts`); writing scripts and starting the clone and scan commands (`src/launch.ts`); sandbox creation, warm adoption, and stop (`src/sandbox.ts`); findings parsing (`src/findings.ts`); the stage protocol and progress reader (`src/protocol.ts`); the telemetry field allowlist (`src/telemetry-fields.ts`).
- What stays in the app: routes and UI, GitHub sessions and OAuth, the Postgres store and schema, admission/allowance/velocity rules (abuse rules, deliberately not public), the cron, GitHub repository listing, dependency checks against cve.now, and the OTLP exporter.

## Invariants

- The model key never enters a sandbox. The sandbox egress policy attaches it to requests for `ai-gateway.vercel.sh`; `AI_GATEWAY_API_KEY` inside the sandbox is a placeholder. Egress is otherwise limited to `github.com` and `registry.npmjs.org`.
- The Deepsec workspace lives outside the checkout. A repository can ship its own `.deepsec/deepsec.config.ts`, which Deepsec would import and run.
- The clone credential is removed from the checkout before any agent reads it.
- The scan command sets `DEEPSEC_INSIDE_SANDBOX=1`. Without it, Codex tries a nested bubblewrap sandbox that cannot start in a Vercel Sandbox; every tool call fails and Deepsec still records the file as `analyzed` with no findings. Coverage counts a file as investigated only when its latest analysis has no `refusal.skipped` entries.
- Deepsec 2.3.10 has no built-in matchers for some languages (Swift among them) and our scaffold-only setup skips its model-generated matcher phase, so a built-in scan can select zero files. The scan script installs `FALLBACK_MATCHER_SOURCE` (`lib/server/scan-script.ts`) into the sandbox; its `prepare` step copies the matcher from `FALLBACK_MATCHER_PATH` and fails with `fallback_setup` if missing. When built-in matching selects no files, the scan rescans, ranks pending files by security-relevant signals, and investigates the top `DEEPSEC_RUN_MAX_FILES` (external scans) or every pending file (Sazabi-member scans, which have no file cap) through `process --manifest`. The report shows `REVIEW MODE fallback`.
- `launchScan` writes the scan script, the clone script, the fallback script, and `FALLBACK_MATCHER_SOURCE` into the sandbox; the fallback `prepare` step copies the matcher from `FALLBACK_MATCHER_PATH` and fails with `fallback_setup` if it is missing.
- A `deepsec process` failure still exports whatever earlier files produced before `failure.json` is written, so the report is `partial` with those findings instead of empty.
- The repository is cloned inside the sandbox by `CLONE_SCRIPT`, a separate detached command whose environment carries the GitHub token through a `GIT_ASKPASS` helper that is deleted right after the fetch; the scan script waits for `clone.json` and never sees the token. Sandboxes are never created with a `git` source.
- Clone/scan phase and failure markers, plus the clone's source-file count, are written to temporary files and renamed into place so concurrent polling never reads half-written JSON or a partial readiness value.
- A non-waiting `getCommand` does not report a detached command's exit code (`@vercel/sandbox` 2.9.2). The worker treats the script's `done` marker or `failure.json` as completion.
- Telemetry fields are an allowlist (`SafeEventFields`). A new field needs an entry in `src/telemetry-fields.ts`; names, URLs, source content, raw errors, and credentials never qualify.

## Limits

- External scans keep the `DEEPSEC_RUN_MAX_FILES` cap (default 40), the 45-minute sandbox, and a hard $50 budget. They require a separate `DEEPSEC_RUN_EXTERNAL_AI_GATEWAY_API_KEY`; never use the shared internal gateway key for external jobs. The external worker passes a $50 model budget to Deepsec's process budget check through a version-guarded adapter, with one-file serial batches and 12 turns to limit overshoot. Missing model-cost usage stops the external scan fail-closed. Deepsec checks spend after each batch, so the final batch can exceed $50; this is a practical ceiling, not a hard billing cap. Internal verified Sazabi members use `DEEPSEC_RUN_AI_GATEWAY_API_KEY` and have no file cap: Deepsec investigates every selected file (no `--limit`, unbounded fallback manifest) with `--concurrency` `DEEPSEC_RUN_MEMBER_CONCURRENCY` (default 8; a 4-vCPU sandbox is mostly waiting on the model) and the default batch size. Their sandbox lives up to `DEEPSEC_RUN_MEMBER_SANDBOX_TIMEOUT_MS` (default 23 hours; Vercel Sandbox allows 24 on Pro/Enterprise, and an adopted warm sandbox adds this to its remaining lifetime, so keep an hour of headroom). The only spend bound is the member ceiling `DEEPSEC_RUN_MEMBER_MAX_COST_USD` (default $1,000), which uses the same Deepsec budget adapter as external scans, so missing model-cost usage also stops a member scan fail-closed. A scan that reaches the ceiling or the sandbox deadline exports what it has and ends `partial` (`time_limit` for the deadline). There is no aggregate spend cap across scans.
